# LED_LIB — библиотека управления светодиодами

Bare-metal библиотека для **1–8 независимых светодиодов** на любом MCU (без RTOS).
Чистый C99, без malloc/free и без зависимости от libc. Доступ к GPIO — только
через пользовательский callback (`led_set_fn`), поэтому библиотека не содержит
аппаратно-зависимого кода.

Ключевые особенности 3.0:

- **Событийная модель времени**: хост сам решает, когда двигать время, и может
  **спать** между продвижениями (`led_advance` + `led_ticks_until_next`).
- **Уровневый выход** 0..`LED_LEVEL_MAX`: аналоговый канал (DAC/ШИМ, 7 ступеней
  яркости) и булевы каналы в одной библиотеке.
- **Владение индикатором**: маяк, предупреждение и обычная индикация
  договариваются о доступе к общему индикатору без конфликтов.
- **Упакованные команды**: 4 байта на пару фаз + счётчик повторов.
- Опциональные модули (`LED_USE_*`), отключаемые ради экономии Flash.

## Возможности

- Независимые конечные автоматы на канал: `led_set_level`, `led_on`, `led_off`,
  `led_toggle`, `led_on_for`, `led_blink`, `led_blink_level`, `led_play`
  (произвольные последовательности, SOS и т.п.).
- 12 встроенных глобальных эффектов (бегущий огонь, мигания, случайные вспышки…)
  с автоповтором и автоостановкой (`led_start_effect_for`, `led_restart_effect_for`).
- Идемпотентный запуск эффектов — безопасно вызывать в цикле опроса.
- Запросы состояния: `led_get_mode()`, `led_get_level()`, `led_is_on()`,
  `led_any_led_active()`, `led_pattern_active()`, `led_effect_active()`,
  `led_effect_remaining()`.
- Настраиваемое число диодов `LED_COUNT` (1..8) через `-D`, полностью
  конфигурационно-независимые эффекты.
- Мутаторы атомарны относительно `led_advance()` при определённых
  `LED_ENTER_CRITICAL()`/`LED_EXIT_CRITICAL()` (см. led.h).

## Установка

**Из GitHub:**

```ini
lib_deps = https://github.com/tama18101971/LED_LIB.git
```

**Вручную:** скопируйте `include/led.h` и `src/led.c` в проект.

## Демо и примеры (CH32V003)

```bash
pio run                     # все примеры сразу
pio run -e ch32v003         # демо: мигание + SOS + эффект + маяк
pio run -e ch32v003-rates   # четыре частоты, скважность 50 %
pio run -t upload -e ch32v003-rates
pio device monitor          # монитор порта (115200)
```

Примеры собираются **из корневого `platformio.ini`**: у них нет собственных
проектных файлов и копий `led.h`/`led.c` — библиотека подключается один раз
через `lib_deps = symlink://.`, а какое именно окружение собирать решает
`build_src_filter` (см. `platformio.ini`).

### `examples/test_ch32v003` — демо возможностей

Эффект + per-LED режимы + владение индикатором + маяк из упакованных
команд. Размер прошивки: 3968 Б Flash, 412 Б RAM.

Диагностика (вывод в UART и аппаратный самотест) в обычной сборке
**выключена** — `-DDEMO_UART=0 -DDEMO_SELFTEST=0` в `build_flags`
окружения `ch32v003` (в `firmware.elf` нет ни одного символа
printf/malloc). Включить: поменять эти `0` на `1`; тогда прошивка
11520 Б Flash / 976 Б RAM.

### Пример «четыре частоты»

`examples/rates_ch32v003` — самый короткий возможный пример: четыре диода
с разными частотами (1 раз в 4 с / 1 раз в 2 с / 1 раз в 1 с / 2 раза
в 1 с) при скважности 50 %, тик 1 мс. Вся «логика» — четыре вызова
`led_blink()` и `led_advance()` в цикле. Размер прошивки: 3376 Б / 408 Б.

## Тесты (без железа)

```bash
pio test -e native     # нужен gcc/clang/mingw в PATH
```

Хост-тесты (самодостаточный раннер, ~380 проверок в конфигурации по умолчанию)

корректность `led_ticks_until_next()` (сценарий сна), уровневый вывод, арбитраж
владения, упакованные команды и события.

## Минимальный пример (опрос 60 Гц)

```c
void led_hw_set(uint8_t id, uint8_t level) {
    /* ваша GPIO-запись: level 0 = гасить, level > 0 = «горит» */
}

int main(void) {
    led_init();
    led_set_callback(led_hw_set);

    /* 1) ЭФФЕКТ СНАЧАЛА: led_start_effect() переводит ВСЕ каналы в режим
     *    EFFECT. Любая per-LED функция, вызванная ПОСЛЕ неё, «отвязывает»
     *    конкретный канал от эффекта. Повторный вызов того же эффекта
     *    идемпотентен и не сбрасывает фазу. */
    led_start_effect_for(LED_EFFECT_EMERGENCY, 5); /* LED2+LED3: 5 вспышек */

    /* 2) ПОТОМ per-LED: эти каналы больше не участвуют в эффекте */
    led_blink(0, 15, 15);    /* LED0 мигает: 250 мс вкл / 250 мс выкл */
    led_on_for(1, 300);      /* LED1 горит 5 секунд (при точных 60 Гц) */

    for (;;) {
        led_process();       /* = led_advance(1): тикают FSM, 60 раз в секунду */
        Delay_Ms(16);        /* ~62 Гц: 1 тик ≈ 16 мс */
    }
}
```

> Важно: ни один вызов API не блокирует процессор. `led_on_for()`, `led_blink()`
> и эффекты только переключают внутренние режимы; фактическое срабатывание
> делает `led_advance()`/`led_process()`, который нужно вызывать периодически.

## Спящий хост (таймер пробуждения)

Тик — единица времени хозяина (1 мс, 1/60 с, 1/1000 с — что угодно).
Никаких внутренних источников времени у библиотеки нет: она сообщает, сколько
тиков можно не просыпаться.

```c
while (led_ticks_until_next() != LED_TICKS_FOREVER) {
    program_wakeup_timer(led_ticks_until_next());  /* тик = ваша единица */
    sleep();
    led_advance(elapsed_ticks);                    /* сколько реально прошло */
}
```

Гарантии:

- после `led_advance(ticks)` состояние выходов соответствует времени `t+ticks`;
- если за один вызов пересечено несколько переходов, они применяются
  **все и по порядку** — переход не «пропускается»;
- `led_advance(1)` × N тождественно `led_advance(N)`: та же последовательность
  вызовов callback и то же конечное состояние;
- тики без переходов проматываются за O(1), поэтому `led_advance(1000)`
  не дороже `led_advance(1)`.

## Разные частоты на разных диодах

Каждый канал — отдельный конечный автомат, поэтому частоты не связаны.
Это ровно то, что делает `examples/rates_ch32v003`:

```c
/* тик = 1 мс, скважность 50 % */
led_blink(0, 2000, 2000);   /* LED0: 1 раз в 4 с  */
led_blink(1, 1000, 1000);   /* LED1: 1 раз в 2 с  */
led_blink(2,  500,  500);   /* LED2: 1 раз в 1 с  */
led_blink(3,  250,  250);   /* LED3: 2 раза в 1 с  */
```

Периоды задаются в тиках, а не в миллисекундах, поэтому дрейфа нет: каждый
цикл — новый отсчёт с нуля. Правил два:

- **тик должен быть заметно быстрее самой быстрой частоты**: для вспышки
  100 мс раз в 500 мс достаточно тика 10–50 мс, 1 мс — с большим запасом;
- **период должен помещаться в таймер канала** (uint16, до 65535 тиков):
  при тике 1 мс это 65 секунд. Для более длинных циклов — снизить частоту
  тика или перейти на упакованные команды (32-битный таймер, до 1032192
  тиков).

Проверено тестом `test_independent_rates()`: за 4 секунды диоды дают ровно
1 / 2 / 4 / 8 вспышек, каждая длиной ровно заданную (и 100 мс, и
скважность 50 %), вспышки стартуют на тиках 1, 1+period, 1+2·period, … —
и пакетный `led_advance(1000)` для спящего хоста даёт тот же результат.

## Уровни и аналоговый канал

Выход каждого канала — число 0..`LED_LEVEL_MAX`, а не bool: библиотека
оперирует числами, а что с ними делать (включить пин, записать в DAC, задать
ШИМ) — забота callback'а.

```c
static const uint8_t dac_code[LED_LEVEL_MAX + 1] = { 0, 34, 68, 102, 136, 170, 204, 238 };

void led_hw_set(uint8_t id, uint8_t level) {
    if (level > LED_LEVEL_MAX) level = LED_LEVEL_MAX;
    out_set_stc(dac_code[level]);   /* 0 = канал выключен */
}

/* обычная яркость фонаря — статический уровень */
led_set_level(0, 5);        /* TURBO */
/* вспышка на текущей яркости, затем полное гашение */
led_blink_level(0, 5, 15, 0, 45);
```

## Владение индикатором

Арбитраж — на уровне подсистем, а не выводов: маяк умеет гасить «своё» целиком
и не трогает чужое.

```c
/* маяк забирает индикатор, если тот свободен */
if (led_claim() == LED_OWNER_NONE) {
    led_set_owner(LED_OWNER_BEACON);
    led_packed_run(beacon, LED_ARRAY_LEN(beacon));
}

/* гасим только «своё»: SOS на другом канале продолжается */
if (led_stop_owner(LED_OWNER_BEACON)) { ... }

/* хост спрашивает «идёт ли сейчас индикация?» */
if (led_pattern_active()) { ... }
```

Владение снимается само, когда все таймерные паттерны завершились
(проверка — в конце `led_advance()`). Объявлять владение нужно вместе
с запуском паттерна, одним блоком кода.

## Упакованные команды

Для хостов, у которых каждый байт на счет: одна команда = 4 байта и описывает
**пару фаз** вместе со счётчиком повторов и маской каналов.

```c
static const uint32_t beacon[] = {
    LED_CMD(0x1, 1, 15,  60, 3, 0),   /* одна вспышка уровня 3 */
    LED_CMD(0x1, 1, 15, 420, 3, 0),   /* вторая, с длинной паузой */
    LED_CMD(0x1, 1, 15,  60, 3, 0),   /* третья */
    LED_SYS_REP_START                 /* повторять до снятия владения */
};
led_packed_run(beacon, LED_ARRAY_LEN(beacon));
```

Длительности кодируются макросом времени (деление только при сборке, в рантайме —
сдвиги). Значения до 63 тиков кодируются точно; для больших относительная
погрешность не хуже 1/32 (теоретический предел формата 32 бит).

## led_process() из прерывания

Если `led_advance()` вызывается из таймерного прерывания, а остальной API —
из главного цикла, определите критическую секцию, чтобы мутаторы были
атомарными относительно обработчика:

```c
#define LED_ENTER_CRITICAL()  __disable_irq()
#define LED_EXIT_CRITICAL()   __enable_irq()
```

Подробно — раздел «Модель вызовов и потокобезопасность» в `include/led.h`.

## Настройка

```ini
build_flags =
    -DLED_COUNT=6                 ; 1..8 каналов (маски uint8_t)
    -DLED_LEVEL_MAX=7             ; 1..255, диапазон уровней вашей аппаратуры
    -DLED_USE_SEQUENCES=0         ; убрать led_play() и поля SEQUENCE
    -DLED_USE_EFFECTS=0           ; убрать всю подсистему эффектов
    -DLED_USE_PACKED_COMMANDS=1   ; упакованные команды (по умолчанию 1)
    -DLED_USE_EVENTS=1            ; события переходов (по умолчанию 0)
    ; или точечно: LED_USE_RUNNING_EFFECTS, LED_USE_PINGPONG_EFFECT,
    ; LED_USE_BLINK_EFFECTS, LED_USE_MULTI_BLINK_EFFECTS,
    ; LED_USE_RANDOM_EFFECT, LED_USE_HOLD_EFFECTS
    -DLED_ENTER_CRITICAL='portENTER_CRITICAL()'
    -DLED_EXIT_CRITICAL='portEXIT_CRITICAL()'
```

## Ресурсы (CH32V003, -Os, RV32EC; вклад библиотеки = сборка с ней минус сборка без неё)

| Конфигурация | Flash | RAM |
|--------------|-------|-----|
| 1 канал, только упакованные команды (`LED_COUNT=1`, эффекты и последовательности выключены) | **1244 Б** | **48 Б** |
| То же, 3 канала (`LED_COUNT=3`) | 1532 Б | 68 Б |
| 1 канал, только последовательности (альтернатива упакованным) | 792 Б | 28 Б |
| 1 канал, оба модуля | 1408 Б | 56 Б |
| Подмножество ТЗ целиком (+последовательности, +события) | 1620 Б | 60 Б |
| Всё включено, `LED_COUNT=4` | 2660 Б | 124 Б |
| Прошивка демо целиком (SDK + библиотека, без диагностики) | 3968 Б | 412 Б |

Производные величины: общее ядро ≈ 660 Б, модуль упакованных команд ≈ 580 Б,
модуль последовательностей ≈ 130 Б.

> **Что выбрать, если важна экономия.** Упакованные команды выигрывают
> только когда таблица паттернов лежит в **RAM** или вычисляется в рантайме
> (тогда 4 байта на пару фаз против 4 байтов на фазу — вдвое меньше данных). Если
> таблицы объявлены `static const` (Flash), то они бесплатны по RAM, и обычные
> последовательности оказываются и компактнее по коду: тот же маяк из
> 7 шагов — **792 Б Flash / 28 Б RAM** против **1244 Б / 48 Б** у упакованных
> команд. Разница — 452 Б Flash и 20 Б RAM.

Прочие характеристики:

| Параметр | Значение |
|----------|----------|
| Состояние канала | 20 Б с последовательностями, 10 Б без них |
| Состояние упакованного паттерна | 21 Б (независимо от `LED_COUNT`) |
| `led_advance()` | O(LED_COUNT) на тик с переходом, O(1) на тик без перехода |
| Деление/умножение | нет в рантайме (в макросах кодирования — есть, но они сворачиваются при сборке) |
| Зависимости | нет libc (`<stddef.h>` — freestanding-заголовок) |

## Миграция с 2.x

1. В callback'е вывода: `bool state` → `uint8_t level`
   (в теле `if (state)` → `if (level)`).
2. В инициализаторах шагов: `{ true, 10 }` → `{ 1, 10 }`, `{ false, 5 }` → `{ 0, 5 }`.
3. Всё остальное совместимо: `led_process()` = `led_advance(1)`, эффекты,
   последовательности и запросы состояния не менялись.
